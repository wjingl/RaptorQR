# RaptorQR 彩色化（CimQR 混合彩色编码）

## 产物
- **`RaptorQR_彩色版.html`** — 彩色化后的单文件应用（与 `RaptorQR_离线单文件版.html` 同级、可离线使用）。
- `cimqr_codec.js` — 彩色编解码核心（纯 JS，无依赖，可独立测试）。
- `build_color.js` — 构建脚本：把 codec 注入 3 个 worker 并修补主 bundle，重新生成单文件。
- `cdp_drive.js` — 真实浏览器（CDP 协议）UI 驱动 + 彩色帧捕获。
- `test_browser_e2e.js` / `test_tolerance.js` / `test_e2e.js` / `test_codec.js` — 分层功能验证。

## 使用方法
打开 `RaptorQR_彩色版.html` → Sender → **Advanced settings** → QR encoder 选择 **Color CimQR**
→ 输入文本或选文件 → Start。

**QR size（真实档位，QR 版本式阶梯）**：彩色模式的下拉显示 `Cim 40×40 … Cim 112×112`——
固定格 8px/间距 9px（与 libcimbar 同思路），改变**网格每边格数与画布尺寸**：

| 档位 | 网格 | 数据格 | 帧容量（包裹包/负载） | 说明 |
|---|---|---|---|---|
| V10 | 40×40 | 1232 | 616 / 604 B | 最易采集：同显示尺寸下格子为 112 档的 **2.8×** |
| V15 | 48×48 | 1920 | 1116 / 1104 B | |
| V20 | 56×56 | 2736 | 1616 / 1604 B | |
| V25 | 64×64 | 3680 | 2116 / 2104 B | |
| V30 | 80×80 | 5952 | 3491 / 3479 B | 默认（版本 30） |
| V35 | 104×104 | 10320 | 6116 / 6104 B | |
| V40 | 112×112 | 12032 | 7241 / 7229 B | 最大容量（与旧版一致） |

相机负担 = 每边格数：V10 只需分辨 40 格（V40 的 1/2.8），图案点像素大 2.8×，
远距/低分辨率下稳定识别；低档解码也快 8-10×（40×40 ≈ 7ms vs 112×112 ≈ 60ms）。
符号尺寸自描述（TL 角 5 模块标记码：4bit 档位 + 1bit 偶校验），接收端自动适配任意档位；
帧头格式字节 = 档位索引+1（0x01 = 112×112，向后兼容旧帧）。
接收端：Receiver → Start Scan 对准屏幕，自动识别彩色符号（黑白 QR 模式完全兼容）。
**多路并发**：彩色模式支持 Parallel QR（1/2/4/6/8 每帧），网格内同时显示多个彩色符号，
每帧可解出多个包（如 4 并行 → 2176×2176 画布、每帧 4 包）；接收端一帧解码全部符号。
**彩色尺寸可调**：Advanced settings → **Color size (彩色尺寸)** → Compact 544 / Standard 1088（默认）/ HD 2176
（Compact 适合性能弱设备与近距离，HD 适合大屏；接收端自适应任意分辨率）。
**非整数倍率渲染精确对齐**：解码端按格起点图像相位（H 实测映射 + 局部倍率 + y 耦合梯度）
逐格生成相位感知模板，任何渲染倍率下采样像素与图案像素精确一致（整数/半倍率自动退化为旧行为）；
R 测量误差导致硬帧时按 finder 跨度 / 帧尺寸倍率逐模式兜底。
Compact 544 支持 112（0.5×，历史兼容）与 64/56/48/40 网格；104/96/80 网格格点 <0.7px 亚像素不可读。
**界面中英双语**：所有选项/按钮/区域标题均带中文括号翻译（如 "Color CimQR (彩色高速)"）。

## 性能（真实场景相机流实测）
- **解码 13–57ms/帧**（符号占画面 75%，含帧间复用）——等效 **17–76 帧/s**（旧版每秒 1-2 帧，提升约 20-40 倍）
- **帧间复用（tracking）**：相邻帧画面几乎不变时直接沿用上次单应采样（跳过检测），~36ms/帧
  （软判决层命中，与阶梯成功层一致）；画面抖动/切换时自动回退全检测
- **帧哈希去重**：发送端循环播放时重复帧占大多数，decode worker 用廉价像素哈希命中历史帧
  直接跳过（包必重复，dedup 兜底）——重复帧零解码开销
- **实时帧保最新**：decode worker 处理中到达的相机帧不排队，只保留最新一帧——解码慢于帧率时
  始终处理最新画面，消除积压与陈旧延迟（配合包级去重+累积，丢帧不影响正确性）
- 检测器重写：单遍行扫描 + 行间投票（原每候选 3 次全行扫描 + O(n²) 合并）；精化改为局部窗口
  双向 run 匹配（亚像素、抗模糊）；采样单应内联（消除每点数组分配）、NSP 上限 6（-44% 采样）
- **低倍率奇偶模板**：0.5 倍率（544px/格 4px）下格起点奇偶导致采样像素与符号 floor 错位 1，
  按格 x/y 奇偶生成 4 套模板（与渲染交集法像素级一致）；同时修复 px/py 数组浮点除与整数除不一致
  的潜伏 bug（NSP=4 时 floor 错位，此前被 NSP=6 掩盖）

## 彩色化设计（借鉴 libcimbar / cimbar.org 与标准 QR 的融合）

| 要素 | 设计 |
|---|---|
| 固定识别位置 | 保留标准 QR 的**三个角寻像图形（1:1:3:1:1）+ 分隔带 + 顶部/左侧时序图形**，全部黑白高对比；外加 4 模块白色静区；**右下角 5×5 对齐标记**兼作第 4 角点 |
| 彩色图形编排 | **尺寸阶梯**：112×112 标准（数据格 12032）到 40×40（1232 格），格 8px/间距 9px/偏移 8px 恒定（libcimbar 同思路），四角各 9×9 保留区 + 时序带 |
| 非纯色设计 | 每格 = **8×8 子图案（16 种符号 = 4bit）× 4 色（2bit）= 6bit/格**；图案取自 libcimbar 真实位图（亮点数 22–40/64、两两最小汉明距 18/64），抗模糊/白平衡 |
| 色板 | 绿(0,255,0)、青(0,255,255)、黄(255,255,0)、品红(255,0,255)，黑底；解码按**色相+色度**分类（对模糊/曝光鲁棒） |
| 纠错 | GF(256)（本原多项式 0x187）RS(155,125,30)，58 个码字；数据按 155 分块、2 分区交织，抗局部损坏 |
| 帧封装 | `[2B 长度][magic "QC"][1B 格式=档位+1] + RaptorQ 包裹包（≤档位容量）`，与现有协议完全兼容（头 + 负载 + CRC32C） |
| 解码 | **容错尝试阶梯**（见下）→ RS 纠错；黑白帧先做廉价"是否含饱和色"预检，命中才跑彩色解码 |
| 性能 | 解码 **40.7ms/帧**（@1088px，单线程 24.6 帧/s）；渲染 14.4ms/帧；**吞吐 ≈ 212 KB/s（30fps），约为黑白 V10-L 的 34×** |

### 容错尝试阶梯（decodeFrame）
每次尝试 = `[检测降采样, 采样内缩, 软判决, BR标记]`，正常帧第 1 层即命中（零额外开销），困难帧逐级加强。
**检测目标按帧尺寸自适应**（基准 1088 → detTarget，下限 512 上限 2048）：并行网格大画布（2176×2176）下
每符号像素被摊薄，检测分辨率随帧边长同比例提升，保证每帧解出其全部符号。

1. `[512, 7.5, 硬匹配, BR标记]` — 常规路径
2. `[768, 7.5, 硬匹配, BR标记]` — 小模块检测加强
3. `[512, 6, 硬匹配, BR标记]` — 采样内缩抗边界混色
4. `[512, 6, 软判决, BR标记]` — 连续彩色度 + 模板相关打分（抗重采样/模糊侵蚀），2×2 邻域面积采样
5. `[512, 6, 软判决, 平行四边形]` / `[512, 7.5, 硬, 平行四边形]` — 标记误检时兜底
6. `[512, 4.5, 软判决, BR标记]` / `[768, 6, 软判决, BR标记]` / `[2048, ...]` — 重度模糊/大画布

BR 对齐标记检测：中心暗 + 半径 1 mod 处 8 点白环带验证（数据区不存在 18px 宽白域，强区分）→ 暗点质心亚像素精化 → 4 真实角点解真单应（透视不再是平行四边形近似）。

## 功能验证（全部基于出厂 `RaptorQR_彩色版.html`）

### A. 真实启动与显示（CDP 驱动真实 Edge，非虚拟时间）
UI 全自动：Text 页签 → 粘贴 31.5K 文本 → Advanced → 选 **Color CimQR** → Start Live QR
→ 画布 **1088×1088** 实时播放（RAF 62fps），状态行 "Live QR running (2 packets, 4 per tick)"。
画布像素统计：绿 42.5 万、青/黄/品红 各 ~3800、黑 35.2 万、白 39.5 万，**other=0**（全部像素落在设计色板内）。

### B. 真实彩色传输接收（端到端逐字节还原）
浏览器捕获的真实帧 PNG → **出厂 decode worker**（vm 沙箱 + 真实 RaptorQ WASM）→
RaptorQ 解码 + 解压 → 文本 31499 字符与发送内容**逐字节一致**（含中文）。

### C. 容错识别（对真实捕获帧施加畸变，出厂 worker 解码）
| 畸变 | 结果 |
|---|---|
| 干净帧 / 旋转 2° / 旋转 5°+缩放 0.8 / 缩放 0.7 / 缩放 1.25 / 平移 +80,+60 / 亮度 ×0.7 / 亮度 ×1.3+20 / 透视 ~4% | ✓ 文本精确还原 |
| 轻度模糊（box r=1，≈轻微失焦） | ✓ 文本精确还原 |
| 重度模糊（box r=2/3，明显失焦） | ✗ 1px 细笔画被物理抹除，超出该格径的信息极限 |

### D. 高效工作
- 解码 40.7ms/帧（24.6 帧/s 单线程）≥ 相机分析 5–10 帧/s 需求的 2.5–5×
- 渲染 14.4ms/帧；帧容量 7229B → **≈212 KB/s @30fps（黑白 V10-L 的 ~34×）**

## 漏帧/慢解码应对（接收端设计）
- **包级缓存与去重**：decode worker 内 `dedup` 集合按包负载 ID 去重，`decoder`（RaptorQ）跨帧持续累积；每个包先过 **CRC32C** 校验才被接受——误码帧/误读帧永远不会污染缓存。
- **不等整轮**：RaptorQ 喷泉码特性——任意 K 个互异包（源或修复）即可解出该代；发送端按播放策略（fast-start/balanced/even-spread）交错源包与修复包循环播放。漏一帧只损失该包，其余帧继续累积；实测 37% 帧丢失（4 源+1 修复，漏 2 帧）仍完整还原（见 `test_accumulation.js`）。
- **解码慢于刷新**：帧队列对实时帧上限 60 帧、超出丢最旧；由于去重+累积，丢帧只降低收集速率、不影响正确性（重复帧直接被去重丢弃，不重复推给解码器）。
- **多包真实链路**：CDP 注入 30KB 随机文件 → 6 包轮换播放 → 捕获全部 6 帧（漏 1 帧）→ 真实 decode worker 累积 5 个唯一包即还原 30000 字节（`cdp_multipacket.js` + `test_multipacket.js`）。
- **扫描生命周期**：每次 Start Scan / 解析 GIF 都新建 decode worker 实例——无跨扫描陈旧状态。

## 发送端播放循环修复（重要）
早期版本 `xo` 中彩色模式把网格强制为 1×1 而 parallelCount 仍为 UI 值 4，导致
`displayFrameCount=ceil(包数/4)=1`：播放永远停在”第 0 帧”，该帧的两个包被当作两块瓦片
**重叠绘制在 (0,0)**，画布恒显示最后一个包 → 多包传输永久卡死。
修复：彩色模式**恢复按用户选择的并行网格**（大瓦片 1088px × Po(o) 网格，瓦片位置不重叠）。
验证：并行=4 时画布 2176×2176、每帧显示 4 个彩色符号，接收端每帧解出其全部符号，
30KB 文件 6 包（4+2 两帧）端到端逐字节还原（`cdp_parallel.js` + `test_parallel.js`）。

## 已知边界
- 推荐相机有效倍率 ≥0.6（符号占画面一半以上）；更低倍率下软判决层仍可工作但成功率下降。
- 重度失焦/运动模糊（>2px）会抹除模板 1px 细笔画——这是当前格径（9px 间距）下的信息极限，属边界可用。
- 30° 以上旋转：寻像行扫描未针对大角度验证（<10° 均实测通过）。
- 黑白模式解码前会先做一次廉价的"是否含饱和色"预检，命中才跑彩色解码，黑白帧开销很小。
